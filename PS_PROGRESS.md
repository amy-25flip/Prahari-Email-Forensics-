## Added 2026-09-10 (second pass): attribution confidence, IP/attachment reputation, deployment config

- **Attribution confidence engine** (`backend/attribution.py`): a transparent 0-100 score over eight weighted evidence factors (receiver attestation, SPF/DKIM/DMARC alignment, domain registration age, header-conflict absence, IP-reputation availability, geolocation availability) minus four penalties (Tor match, hosting/proxy/VPN classification, newly registered domain, header conflicts). Every factor is listed whether it applied or not, so the score is auditable. Hard-capped at 20/100 whenever origin evidence is undetermined, regardless of other signals — no combination of secondary evidence can substitute for a trusted origin. This is a weighted transparency score, not a calibrated statistical probability or proof of actor identity; it answers "how much should an investigator trust this email's origin evidence," which is a distinct question from the existing evidence/fraud score.
- **IP reputation intelligence** (`backend/ip_reputation.py`, AbuseIPDB, opt-in, requires `ABUSEIPDB_API_KEY`): per-hop usage-type classification (hosting/proxy/VPN/ISP), abuse-confidence score, Tor flag, total reports. Extends origin traceability beyond the existing Tor-exit-list-only coverage toward the PS's "VPN, open relay, botnet" correlation ask — still limited to what AbuseIPDB's community reports capture, not a dedicated VPN/botnet detector.
- **Attachment hash reputation** (`backend/attachment_reputation.py`, VirusTotal, opt-in, requires `VIRUSTOTAL_API_KEY`): looks up existing attachment SHA-256 hashes against VirusTotal's multi-engine verdicts. Capped at 4 lookups per analysis (VirusTotal free-tier rate limit); uncapped attachments are explicitly marked `not_checked`, never silently treated as clean. Only a hash is sent, never file content — no dynamic/sandboxed execution *at the time of this entry* (this changed in the 2026-09-11 entry below, which added opt-in sandbox file upload).
- Both new modules follow the existing enrichment convention exactly (gated by the same `enrich`/`live` flag, `requests`-based, explicit timeouts, in-memory TTL cache, never raise to the caller, absent API key degrades to `status: disabled`) and are exposed in `/api/health` as `ip_reputation.configured`/`attachment_reputation.configured`.
- Frontend: new dedicated `AttributionConfidence` panel (score, band, full factor breakdown, caveats) plus `ip_reputation`/`attachment_reputation` sections added to the existing threat-assessment panel.
- `render.yaml` added for Docker-based deployment to Render with env vars for the new and existing optional integrations (marked `sync: false` so secrets are entered in the Render dashboard, never committed). Render's free tier has no persistent disk option -- `/data` (case history, PhishTank cache) does not survive a redeploy or idle-recycle; this was previously and incorrectly described here as persistent.
- Verification (as of this pass, 169 backend tests; superseded by 231 as of the 2026-09-11 entries below): 169 backend tests passed (148 existing + 21 new covering disabled/no-network, missing-key, rate-limit, cache-hit and score-bounds behavior for all three new modules); frontend build and lint passed; local end-to-end smoke test via the built app confirmed the new panels render correctly on a real fixture with no crashes, including the all-disabled (no API keys configured yet) path.

## Added 2026-09-11: blockchain timestamping, at-rest encryption, VT sandbox, ARC verification, fuzzy campaign correlation

- **OpenTimestamps blockchain checkpoint timestamping** (`backend/blockchain_timestamp.py`): anchors a checkpoint hash to the Bitcoin blockchain via the public OpenTimestamps calendar servers, independent of this server. `POST /api/checkpoint/blockchain-stamp` / `POST /api/checkpoint/blockchain-verify`; frontend in `CheckpointTools.jsx`. Confirmation takes hours, not seconds — this is a real limitation of the underlying protocol, not a bug.
- **At-rest field encryption** (`backend/db_encryption.py`, Fernet/`cryptography`): opt-in via `DB_ENCRYPTION_KEY`, wired at `store.py`'s read/write boundary only — the hash chain is always computed over plaintext before encrypt / after decrypt, so tamper-evidence is unaffected. Absent key or a decrypt failure on a legacy row falls back to plaintext, never raises. SQLCipher (whole-DB encryption) was evaluated and rejected: it fails to build on this Windows dev machine (no prebuilt wheel, no native toolchain), confirmed by direct testing, not assumed.
- **VirusTotal sandbox upload** (`backend/attachment_reputation.py::submit_for_sandbox`/`analysis_status`, `backend/engine.py::extract_attachment`): explicit opt-in real-file upload for dynamic analysis, beyond the existing hash-only reputation lookup. Shares the same rate-limit budget as hash lookups. `POST /api/cases/{cid}/attachments/{sha256}/sandbox`, `POST /api/attachments/sandbox/{analysis_id}`; frontend `SandboxSubmit.jsx`.
- **ARC chain verification** (`backend/arc_verification.py`, RFC 8617): validates the Authenticated Received Chain via `dkimpy`'s `dkim.arc_verify()`. Absence of ARC headers is normal (most email is never re-signed) and is not treated as a failure; only a broken/invalid chain is adverse. Wired into `authentication.py` alongside SPF/DKIM/DMARC and rendered generically by the existing `Authentication.jsx` (no frontend change needed — it iterates whatever keys `authentication` returns). Feeds two new `attribution.py` factors (`arc_chain_valid`/`arc_chain_failed`).
- **Fuzzy campaign correlation** (`backend/campaigns.py::body_similarity`): character-shingle Jaccard similarity (pure Python, no native dependency — ssdeep/TLSH were evaluated and also fail to build on this machine) extends campaign grouping beyond the previous exact-match-only (reply address/URL/hash) correlation. Guarded by `MIN_SIMILARITY_TEXT_CHARS` so two short/near-empty bodies can't trivially false-positive.
- These were implemented and committed (`0c765fa`, `a93b6b3`) in the prior session but never logged in this changelog — this entry corrects that, and corrects several now-false "not attempted" statements this file and `CURRENT_STATUS.md`/`PS_ACCEPTANCE.md` previously carried about these five items.
- Independent review (Codex, via the project's standing implement-then-review workflow) on this batch found and fixed 3 issues (`186a1b1`): the sandbox-status endpoint was GET-based and bypassed the peer-limiter/app-header middleware (changed to POST + added rate-limit reservation); `dkim.ARC.verify()` returns Python `None` rather than `CV_Fail` for one specific intermediate-hop failure path, which silently degraded to `status: unknown` (fixed, confirmed via `inspect.getsource`); fuzzy campaign matching could false-positive on trivially short shared text (fixed with the length guard above).
- Verification: 231 backend tests passed (169 + 62 new/updated, including the 3 regression tests for the above review fixes).

## Added 2026-09-11 (third pass): the original Google .eml, real-email validation, team-trained model wired in

The original Google `.eml` referenced as pending throughout this file, `PS_ACCEPTANCE.md`, `CURRENT_STATUS.md` and `AUTHENTICATION_NOTES.md` since the project's earliest checkpoints was located and run through the live pipeline (`POST /api/analyze?enrich=true`) end to end, repeatedly, for the first time. This is one real email, not the broader independently-adjudicated multi-email/false-positive/latency test suite still listed as a submission gate below — but it is the first time *any* real (non-fixture) email has been analyzed by this system, and it immediately found real bugs that 234 unit tests had not:

- **500 crash on the very first real ARC-signed email**: `backend/arc_verification.py` passed dkimpy's raw `bytes` header values straight into the JSON report; every existing test had monkeypatched `str` instead, hiding this. Fixed (`_jsonable()` decode helper), regression test added.
- **ARC chain metadata was silently empty in every report**: the same crash investigation found the chain-building code was reading dict keys (`'d'`, `'i'`) that dkimpy's real `ARC.verify_instance()` never produces (confirmed via `inspect.getsource`, not assumed) — the real keys are `'instance'`/`'as-domain'`/`'cv'`. Fixed; ARC reports now actually show which domain sealed each hop.
- **A transient DNS timeout could apply a real attribution-confidence penalty to a legitimate email**: repeated analysis of the same real email produced different ARC verdicts (`pass` vs `fail`) across identical retries, because `dkim.ARC.verify()` cannot distinguish "no key published / forged seal" from "the DNS query timed out" — both collapse to the same `CV_Fail`. Fixed by tracking transient DNS failures (timeout, no nameserver reachable) separately from definitive negative answers (`NXDOMAIN`/`NoAnswer`) and only downgrading the former to `unknown` rather than `fail`, so `attribution.py`'s `-15` penalty no longer fires for DNS flakiness — while a message with a genuinely absent/forged seal still correctly reports `fail`. Codex's review caught that the first version of this fix was too broad (any DNS exception, including a real negative answer, was being downgraded) before it was committed.
- **The pretrained model false-positived on this real, legitimate email** (100% confidence "phishing"). This was the concrete, real-world case for finishing the team's own fine-tune (see below), not just a documentation caveat.
- **Team-trained model wired in**: `training/train_phishing_model.py` (see the leakage fix in the prior commit) completed a real training run on the team's own curated dataset — 268,211 train / 33,526 validation / 33,527 held-out test rows after deduplication, held-out **test accuracy 99.32%, precision 99.45%, recall 99.11%, F1 99.28%, ROC-AUC 99.96%**. `backend/local_model.py`'s health-check detail previously always claimed "pretrained model, not team-retrained" regardless of which model was actually loaded; now it only claims team provenance when `training_report.json` is actually present next to the model weights (verified, not just a filename check), and cites the real metrics from it. Wired in locally via `MODEL_ID` in the gitignored `backend/serve_local.py` (the 419MB model file is not committed to git — see the "Reproducing the trained model" note below).
- **Validated the fix**: the same real email, re-analyzed with the new model, was correctly classified `legitimate` at 74.3% confidence (was `phishing` at 100% with the old model); overall risk score dropped from 30 ("Review") to 0 ("Low").
- All three code fixes were independently reviewed by Codex before commit, following the project's standing implement-then-review workflow (`803fd1b`).
- **Reproducing the trained model**: the trained checkpoint lives at `training/output/phishing-bert-v1/final/` (gitignored, ~419MB — too large to commit) after running `python training/train_phishing_model.py`. `backend/serve_local.py` (also gitignored) points `MODEL_ID` at that path for local runs. Anyone else running this repo without that local training output will fall back to the public `ealvaradob/bert-finetuned-phishing` checkpoint, as before.
- Verification: 234 backend tests pass.

**Still not satisfied** (this pass narrowed, but did not close, the broader real-email submission gate below): only one real email has been tested, not a representative set; no systematic false-positive rate or end-to-end latency measurement has been done; the DNS-flakiness fix above was validated against one live scenario, not a comprehensive test of every DNS-dependent check under failure conditions.
